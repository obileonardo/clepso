# v0.3 integration plan

Research and verification date: 21 October 2026. This is a proposed scope, not a released feature list.
The public build remains v0.2.0-alpha.5. Goals controls, the Homebrew tap and the approved authentication emails
are complete. Desktop/IDE tracking has an existing implementation behind `ReleaseFeatures.claudeMod`.

## Recommended sequence

| Priority | Outcome | Acceptance evidence |
| --- | --- | --- |
| 1 | Finish the existing desktop/IDE bridge | Desktop-only quota adoption, model/session matching, install/use/remove and a current VS Code panel pass the live runbook |
| 2 | Ship v0.3.0-alpha.1 for bridge validation | Explicit opt-in, honest unavailable/stale states, terminal priority preserved, no prompts/files/credentials forwarded; CI and signed/notarized release checks pass |
| 3 | Consider a read-only Clepso MCP interface | A real client can request an already-collected usage snapshot; output has provenance, timestamps and unavailable states; opt-in disclosure and deletion/disconnect tests pass |
| Later | Phone reset reminders, then optional alarms | Native device prototype, pairing, permission-denied/offline/stale tests and an approved delivery/cost model |

Recommend v0.3.0 for the completed desktop/IDE capability; use `-alpha.1`, `-alpha.2`, etc. for its prereleases.
Use subsequent patch releases for fixes after that release. Keep the mod package's version independent of the
Mac app's version: the existing plugin manifest's `0.3.1` does not mean the app has shipped v0.3.1.
No version or public feature flag is changed by this plan. Phone delivery should not block a smaller desktop release.

## Homebrew and MCP answer different questions

Homebrew already includes an official MCP server through `brew mcp-server`. Its tools help an assistant search,
install, update and remove packages. The existing Clepso tap supplies the package; a second Clepso-specific
Homebrew server would duplicate that role. [Homebrew documentation](https://docs.brew.sh/MCP-Server).

A separate Clepso MCP server could answer “What are my current Claude and Codex limits?” from readings Clepso
already holds. MCP tools expose callable operations and structured results. They do not themselves discover hidden
provider quotas or mandate an always-visible IDE widget. Client support determines how results are displayed.
[MCP tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

Recommended first interface, if implemented:

- A local stdio server, started explicitly by a supported MCP client; no network listener or account credential.
- One bounded `get_limits` tool with an optional provider filter, and a `get_reader_health` tool.
- For each window: provider, window kind, used percentage when reported, reset instant when reported, observation
  time, freshness/state and source. Keep used/remaining semantics explicit; retain legitimate overage values.
- Preserve missing, stale and expected-reset states. Never turn missing data into zero or claim a reset was observed
  just because its expected time passed. Keep manual snapshots distinct from automatic readings.
- Read through a narrow, versioned app snapshot boundary; avoid arbitrary SQL, file paths, transcripts, session
  identifiers, export commands, shell execution, settings writes or credential access.
- Opt in per client. A local server can still return usage information to a client that sends it to a remote model;
  explain that disclosure before connection. Do not add MCP client configuration silently.

`Sources/clepso/main.swift` currently implements installation/status/recovery commands, not this usage API or an
MCP server. Implementation needs a snapshot contract, stale/offline behavior, schema/size bounds and real client tests.
It is not already available via `clepso mcp`.

## Tracking inside Claude Code and IDEs

Use the existing supported mod event route for Claude's Code tab, rather than scraping the window or session text.
`register.js` handles `session.measure`, reads surface/session/version/model facts, builds an allowlisted handoff,
and invokes the fixed local helper. Terminal sessions remain covered by the status-line route. See
[`mod-bridge.md`](mod-bridge.md) and the [official mods API](https://code.claude.com/docs/en/plugins/mods/api).

The current mod forwards readings to Clepso; it does not draw a new usage bar inside Claude. A native in-session
display would be a separate UX change using the host's supported UI API and needs surface-specific verification.
An MCP integration would let an assistant query Clepso, with no guarantee of continuous display or refresh.
None of these routes supplies telemetry that a provider has not reported.

The [21 October desktop result](../qa/2026-10-21-desktop-mod.md) proves helper execution, first-session loading,
context ingestion, model labeling, hook/session matching and exact settings restoration. Its isolated follow-up
verified both quota windows and reset instants through the normal mapper/store without competing terminal readings.
The [VS Code result](../qa/2026-10-21-vscode-mod.md) likewise verified surface detection, quotas/resets, matching
desktop model id and hook identity on extension 2.1.305. Native menu-bar presentation, terminal takeover and
supported-UI removal/discoverability remain open. Keep the shipping flag off until these release gates pass.

## Phone reminders and alarms

Recommend a staged iPhone companion, after the desktop bridge. A Mac-only app or Homebrew package cannot directly
schedule a native alarm on someone's iPhone.

1. Pair an opted-in phone with the same account/device owner. Send only window identity/version, source time,
   expected reset and reminder preference. Revoke access cleanly when either side disconnects.
2. Prototype ordinary notifications first. Once the phone receives a current reset schedule, it can schedule a
   local reminder without requiring a push at the exact reset instant. Its wording must describe an **expected**
   reset; only fresh provider telemetry confirms that usage is available again.
3. Add AlarmKit only as an explicit, separate alarm option for supported devices. Apple provides AlarmKit on
   iOS/iPadOS 26 and requires alarm authorization and a usage description. Its prominent alarms can sound through
   silent/Focus settings, so users must choose them intentionally. See [AlarmKit](https://developer.apple.com/documentation/alarmkit)
   and [Apple's introduction](https://developer.apple.com/videos/play/wwdc2025/230/).

Background pushes are low priority, can be delayed/throttled, and have no delivery guarantee. They can refresh a
schedule, but cannot support an “always immediate” reset promise. A previously scheduled local alarm can also
become outdated while the phone is offline. [Apple background-push guidance](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app).

Before implementation, define schedule freshness/expiry, duplicate suppression, update/cancel rules, UTC/timezone
behavior, offline warnings and permission-denied fallback. Test reset changes, revoked permissions, force-quit,
Mac sleep, phone offline, reconnect, DST and disconnect. Scheduling receipts and actual delivery must be distinct.
A stale or superseded schedule must not be presented as verified availability.

APNs delivery needs a native app identity, device-token lifecycle and a server-side sender. Choose between the
existing account backend and a separate relay only after a small device prototype establishes the requirements.
Server credentials stay server-side; no paid tier, new domain or new mobile-service subscription is assumed.
Android, a Watch app and richer alarm interactions are separate platform scopes.

## Open release gates

- Shipping menu-bar/Settings presentation and takeover without a fresh competing terminal source. Isolated desktop
  and IDE quota adoption is verified; this does not establish that the shipping UI updates correctly.
- Terminal canonical-model/source comparison and native IDE removal UI. Current VS Code surface, quotas/resets,
  desktop model-id agreement and hook matching are verified; post-test capture errors prevented the removal UI check.
- Plugin-manager discoverability: the current desktop manager did not list the directory-backed mod, although it ran.
  CLI cache records can survive removal in a disabled state; document that without rewriting unrelated settings.
- Remaining native accessibility and lifecycle QA, including full VoiceOver, long sleep/restart and older/clean macOS.
- For MCP or mobile delivery, review the proposed UX/data/cost choices before adding those new public capabilities.
